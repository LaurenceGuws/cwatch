Phase 4 — UI Layer Separation (Controller/View-Model + Service + Repository + UI Adapter)

Overview
Goal: Move CWatch toward a clean, predictable architecture where UI never touches domain/data logic directly. Establish a single, global layered structure (no per-module nested layers) that is enforced across the app. This phase focuses on UI layer separation, leaving persistence standardization for the next phase.

Principles
- UI only talks to Controllers/ViewModels.
- Controllers/ViewModels orchestrate Services and call UI Adapters for dialogs/snackbars/menus.
- Services contain domain logic only (no Flutter imports).
- Repositories encapsulate data access (filesystem, SSH, caches, config).
- UI Adapters are the only layer touching Flutter UI APIs (BuildContext, dialogs, SnackBars, menus).
- Shared layer is for utilities and cross-cutting concerns only.

Target Structure (Global, Single-Layered)
- lib/app/controllers/
- lib/app/services/
- lib/app/repositories/
- lib/app/adapters/
- lib/data/sources/
- lib/data/models/
- lib/ui/views/
- lib/ui/widgets/
- lib/ui/bindings/
- lib/shared/ (utilities only)

Scope for Phase 4
- Establish new folder structure and base interfaces.
- Pilot migration on File Explorer (largest UI-service mix).
- Document rules and add a checklist for future refactors.
- Ensure no regressions in UI behavior; run flutter analyze.

Phase 4.1 Audit Findings (initial pass)

File Explorer
- UI-to-service couplings:
  - `lib/shared/views/shared/tabs/file_explorer/file_explorer_tab.dart` constructs `FileExplorerController` and invokes `FileOperationsUiHandler`, `FileEditingService`, `DeleteOperationsHandler`, `ClipboardOperationsHandler`, `ExplorerOsDragManager` directly with `BuildContext` for dialogs/snackbars and drop handling.
  - `lib/shared/views/shared/tabs/file_explorer/file_explorer_controller.dart` orchestrates `ExplorerOps`, `PathLoadingService`, `FileOperationsService`, `FileOperationsUiHandler`, `FileEditingService`, `DeleteOperationsHandler`, `ClipboardOperationsHandler`, and `ExplorerUiAdapter`.
- UI leakage points:
  - `lib/shared/views/shared/tabs/file_explorer/file_editing_service.dart` imports Flutter and uses `BuildContext` + `ScaffoldMessenger` for snackbar feedback.
  - `lib/shared/views/shared/tabs/file_explorer/file_operations_ui_handler.dart` is UI-bound (dialogs, progress UI, FilePicker) but lives alongside services.
  - `lib/shared/views/shared/tabs/file_explorer/clipboard_operations_handler.dart` and `lib/shared/views/shared/tabs/file_explorer/delete_operations_handler.dart` take `BuildContext` and show snackbars.
  - `lib/shared/views/shared/tabs/file_explorer/explorer_os_drag_manager.dart` uses `BuildContext` and UI adapter to initiate drag.
  - `lib/shared/views/shared/tabs/file_explorer/external_app_launcher.dart` takes `BuildContext` for error snackbars.
- Existing UI adapter:
  - `lib/shared/views/shared/tabs/file_explorer/explorer_ui_adapter.dart` wraps dialogs/snackbars/menus, but several services still call UI directly.

Terminal / Editor
- UI-to-service couplings:
  - `lib/shared/views/shared/tabs/terminal/terminal_tab.dart` calls `RemoteShellService.createTerminalSession` directly and manages SSH lifecycle in UI state.
  - `lib/shared/views/shared/tabs/editor/remote_file_editor_loader.dart` reads/writes via `RemoteShellService` inside UI widget.
  - `lib/shared/views/shared/tabs/editor/remote_file_editor_tab.dart` saves via callback that often writes to `RemoteShellService` in callers.
- UI leakage points:
  - None observed in `lib/services` for terminal/editor flows, but UI is tightly coupled to SSH services without controller/service separation.

Docker
- UI-to-service couplings:
  - `lib/modules/docker/ui/widgets/docker_overview_actions.dart` calls `DockerClientService`, `RemoteShellService`, `PortForwardService`, and `BuiltInSshKeyService` directly from UI actions.
  - `DockerOverviewActions` also builds UI dialogs and snackbars inline.
- UI leakage points:
  - `lib/services/ssh/ssh_auth_prompter.dart` is a UI dialog helper inside `lib/services/` and depends on Flutter + `BuildContext`.

Servers
- UI-to-service couplings:
  - `lib/modules/servers/ui/widgets/resources_tab.dart` constructs `ResourceParser` (SSH runner) in the UI and calls `collectSnapshot` directly.
  - `lib/modules/servers/ui/server_tab_builder.dart` wires `RemoteShellService` directly into tabs (Terminal, Explorer, Editor), and `_EditorTabLoader` writes remote files directly.
- UI leakage points:
  - `ResourceParser` is a service-like class under `lib/modules/servers/ui/` rather than a services layer, and it calls SSH directly.

Notes
- `lib/services/ssh/ssh_auth_prompter.dart` is the only `lib/services` file with direct Flutter UI usage identified in this pass.
